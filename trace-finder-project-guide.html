Tracefinder Project Guide

A beginner-friendly explanation of the Java project structure, execution flow, files, objects, and core language concepts.

Tracefinder is a command-line application that reads a rulebook CSV and a log file, converts text into Java objects, analyzes the entries, and writes a report.

1. What the Project Does

rules.csv
   |
RulebookReader
   |
Rulebook object

logs.txt
   |
LogFileReader
   |
LogEntry objects + MalformedLine objects
   |
LogAnalyzer
   |
AnalysisResult
   |
ReportWriter
   |
output-report.txt

The application performs five broad jobs: read configuration, read logs, classify and analyze entries, assemble results, and format output.

2. Project Structure

trace-finder/
|- pom.xml
|- README.md
|- sample-data/
|  |- rules.csv
|  `- logs.txt
`- src/
   |- main/java/com/tracefinder/
   |  |- Main.java
   |  |- model/
   |  |- reading/
   |  |- processing/
   |  `- writing/
   `- test/java/com/tracefinder/
      |- processing/
      |- reading/
      `- writing/

src/main/java contains application code. src/test/java contains automated tests. This is Maven's standard layout, so Maven knows automatically what to compile and test.

The com.tracefinder package and its subpackages organize names and responsibilities. The model package represents data, reading parses input, processing applies business rules, and writing creates the report. This separation keeps one class from becoming responsible for everything.

3. Program Execution

The JVM begins at Main.java's public static void main(String[] args). The method validates three command-line arguments, converts them to Path objects, reads the rulebook, reads the log, analyzes the parsed data, and writes the report.

Rulebook rulebook = readRulebookOrExit(rulebookPath);
LogFileReader.ParsedLogFile parsedLogFile = readLogFileOrExit(logFilePath);
AnalysisResult result = new LogAnalyzer()
        .analyze(parsedLogFile.entries(), rulebook,
                 parsedLogFile.malformedLines());
writeReportOrExit(result, outputPath);

Main is an orchestrator. It does not parse, count, sort, or format data itself. That makes the actual rules easier to test independently.

4. Build Configuration

pom.xml

This Maven file identifies the project as com.tracefinder:tracefinder:1.0-SNAPSHOT, requests Java 17, declares JUnit 5 for tests, configures Surefire to run tests, and configures the Shade Plugin to create a runnable JAR whose entry point is com.tracefinder.Main.

Maven is a build tool. It downloads dependencies, compiles source files, runs tests, and packages the application.

README.md

The README documents the architecture, command syntax, business rules, build command, run command, and test command. It is for people using or learning the project; it is not part of the running program.

5. Model Classes

LogEntry.java

A LogEntry represents one successfully parsed line. It stores the line number, LocalDateTime timestamp, level, IP, resource, action, and original text.

It is a Java record. A record automatically supplies a constructor, accessors such as entry.level(), equals, hashCode, and toString. Records are suitable for data values that do not need much mutable behavior.

MalformedLine.java

This record stores a line number and raw text for a line that could not be parsed because it was blank, had the wrong number of fields, or had an invalid timestamp.

UnknownPatternLine.java

This record stores a structurally valid line whose level is not in the rulebook. It is separate from a malformed line because the timestamp and five fields are still usable.

Rulebook.java

This is a normal class rather than a record because it provides behavior: isKnownLevel, severityOf, levelsInFileOrder, and asMap.

Its LinkedHashMap<String, Integer> maps levels to severity scores and preserves CSV order. private hides the field, and final prevents the field reference from being replaced after construction.

AnalysisResult.java

This record is the complete output of analysis: activity counts, flagged entries, IP counts, unknown patterns, and malformed lines. It is the data handoff between processing and writing.

6. Reading Classes

RulebookReader.java

This class reads all CSV lines, skips the header, ignores blank rows, splits each remaining row into two fields, trims the values, parses the score with Integer.parseInt, and builds a Rulebook.

RulebookFormatException is a custom checked exception. It communicates that the file could be read but its contents violate the expected format. The caller must catch it or declare it.

LogFileReader.java

This class reads every log line and assigns one-based line numbers. Its nested ParsedLogFile record groups valid entries and malformed lines in one return value.

tryParseLine returns a LogEntry when the line has exactly five fields and a valid timestamp. Otherwise it returns null, and the caller creates a MalformedLine.

The reader does not decide whether a level is known. That is a business rule, so it belongs in the processing layer.

7. Processing and Business Rules

LogAnalyzer.java

The analyzer creates four results through private helper methods. Keeping each calculation separate makes the logic easier to read and test.

Activity summary: starts every rulebook level at zero, then counts only known levels. The merge method inserts one or increments an existing count.

Flagged entries: finds the lowest severity using Collections.min. Every known level above that baseline is flagged. A comparator sorts by severity descending and timestamp ascending.

Suspicious activity by IP: counts every valid entry, including unknown levels. A temporary HashMap is used while counting because order does not matter. The final LinkedHashMap preserves sorting by count descending and IP ascending.

Unknown patterns: selects valid entries whose levels are absent from the rulebook, converts them to UnknownPatternLine values, and sorts them by original line number.

The code uses lambdas such as e -> rulebook.severityOf(e.level()) and method references such as LogEntry::timestamp. These are short ways to provide functions to sorting APIs.

8. Writing the Report

ReportWriter.java

The writer receives an AnalysisResult, formats sections into a StringBuilder, and saves the result with Files.writeString.

The report includes the generated time, activity summary, flagged entries, suspicious IP counts, unknown patterns, and malformed lines. The original raw lines are retained so the report can show exactly what appeared in the source file.

StringBuilder is appropriate for constructing text incrementally. The writer uses Map.Entry to iterate over key-value pairs in the maps.

9. Tests

LogAnalyzerTest.java

This JUnit class verifies activity counts, rulebook order, flagging, severity and time sorting, IP sorting, and unknown-pattern order. Helper methods create test objects without repeating the full constructor call.

LogFileReaderTest.java

This class uses temporary files to test valid lines, blank lines, missing fields, wrong delimiters, bad timestamps, and unknown levels. It proves that unknown levels remain valid entries while malformed syntax does not.

There is currently no ReportWriterTest.java in the workspace, so formatting is not directly covered by an automated test.

10. Sample Data

sample-data/rules.csv

The sample rulebook defines INFO -> 1, WARN -> 3, ERROR -> 5, and ALERT -> 9. INFO becomes the baseline, while the other known levels are flagged.

sample-data/logs.txt

The sample log demonstrates normal entries, unknown levels such as CRIT and TRACE, lowercase levels, blank lines, missing fields, wrong delimiters, and invalid timestamps.

Level matching is case-sensitive: INFO is known, but info is unknown.

11. Why This Design?

The project separates concerns so each class has a focused responsibility. A single large method could do all of this, but it would mix filesystem operations, parsing, business rules, sorting, and presentation. That would make changes and tests harder.

The collection choices also match the jobs: List preserves sequences, HashMap supports counting without ordering requirements, and LinkedHashMap preserves a deliberate output order.

This is intentionally a small learning project. A production version might use a full CSV parser, immutable defensive copies in Rulebook, stronger validation, and more writer tests. The current design keeps the fundamental ideas visible.
